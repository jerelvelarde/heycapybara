# Clean onboarding design

Approved by the user on September 24, 2026. Amended after code review on September 25, 2026 to match the shipped behavior. Replaces the notch onboarding and the notch placement (`2026-09-23-notch-onboarding-proposal.md`).

## Decision

Remove both halves of the notch flow: the four-step tour that drops from the notch (with its draggable app tile and bottom-of-screen helper) and the "By the notch" companion placement. The floating companion (Capybara or Kite) becomes the only placement. First-run setup moves to a small, centered setup window with three screens.

Rejected: onboarding inside the workspace window (a 1240×820 window for a three-click task, and `App.tsx` grows), and speech bubbles anchored to the capybara (chat-sized, positioned anywhere on screen, and it reintroduces the positioning code this change removes).

## Removed

- `src/Notch.tsx`, `electron/notch-geometry.ts`, `tests/notch-geometry.test.ts`, and the `.notch*` and `.placement-*` styles.
- The notch window and its state in `electron/main.ts`: sizing, expansion, inset refresh, the Accessibility drag guide, the outgoing `.app` drag and its icon.
- The native helper's `--notch-inset` command.
- The `placement` preference, the `Placement` type, `Settings.placement`, and the placement choice in Settings.
- IPC: `setPlacement`, `setNotchExpanded`, `startAppDrag`, `openAccessibilitySettings`, `closeAccessibilityGuide`, `revealAppInFinder`.

## Setup window

A new on-demand window, created when setup is needed and destroyed when it ends: 520×600, centered on the primary display's work area, not resizable, minimizable or full-screenable, hidden-inset title bar titled "Welcome to OpenMuse" with only the close control enabled, not always on top. Because a hidden-inset title bar leaves no native drag strip, the whole top strip of the window (`.onboarding-titlebar`) is a drag region so the window can still be moved, and the strip stays at the top while the content scrolls. It loads the renderer with `?onboarding=1` and uses the same sandboxed preload, navigation denial and window-open denial as the other windows.

The workspace never opens at launch, whether or not setup is needed. While setup is incomplete, the setup window is shown and focused, and the companion and its chat tray are hidden. Activating the app from the Dock focuses the setup window instead of opening the workspace. When setup completes or is skipped, the window is destroyed and the companion appears. Replay after setup has ended creates a fresh window, so the renderer starts on Welcome; replaying while the setup window is still open brings it forward on its current step.

## Screens

1. **Welcome.** The selected companion sprite (Capybara or Kite), "Meet your new work buddy.", one sentence about teaching a workflow once, and **Get started**.
2. **Permissions.** One screen, two rows:
   - **Accessibility**, to follow along while you record. **Allow**.
   - **Screen Recording**, optional, to attach a screenshot when you choose. **Allow**.

   **Allow** calls the existing `permissions(kind)` request, so macOS shows its own prompt and lists OpenMuse in System Settings (development builds may list Electron or kite-recorder instead). After a request, a row that is still off shows "Waiting for System Settings" and an **Open System Settings** button that opens that permission's pane. Accessibility adds "Already on? Turn it off and on again."; Screen Recording adds "macOS may ask to reopen OpenMuse." A granted row shows "Allowed" with a check. The Allow and Open System Settings buttons carry per-row `aria-label`s (for example "Allow Accessibility") so assistive tech can tell the rows apart. **Continue** never depends on which permissions are granted, but it is disabled while a permission request or **Open System Settings** is in flight; while Accessibility is off, a note says recording needs it and it can be allowed later in Settings.

3. **Ready.** The sprite, "You’re all set.", one line about clicking the companion to chat or hovering to record, **Start using OpenMuse**, and an **Open the workspace** button that completes setup and opens the workspace.

Three dots show progress. The heading takes focus on each screen change. Screen transitions are immediate under reduced motion. There is no model or Intelligence key entry; those stay in Settings.

## Behavior

- **Who sees it.** Before `Store.load()` creates the `library` folder, `startupPreferences` checks for it: an existing folder means a returning install. Only a missing folder (ENOENT) counts as new; any other error fails startup. A stored preferences file decides for either kind of install. Without one, a new install shows setup and saves its default preferences at once, so if that launch fails later or the user quits during setup, the next launch shows setup again; quitting never counts as a skip. A returning install without a file skips setup and writes nothing: older builds only saved the file after a change, so an upgraded install may have none. A stored file without `onboardingComplete` still loads as complete. Settings → Desktop companion → **Replay setup** and the menu-bar **Replay setup** reopen it.
- **Replay is refused during a recording.** The floating companion carries the always-visible recording indicator and its Stop button, and replaying setup hides the companion and its chat tray. So while a recording is active or still starting, both **Replay setup** entry points refuse with "Stop the recording before replaying setup." before touching preferences. Settings also disables its button, with that message as its tooltip, while a recording is active.
- **Recording is refused while setup is open.** Setup hides the companion, so a recording started then would run with the always-visible indicator and its Stop button hidden. The workspace can still be open during setup (⌘⇧K, the menu bar's **Open OpenMuse**, or after Settings → **Replay setup**), so `startRecording` refuses with "Finish setup before starting a recording." before it checks Accessibility. This rule and the replay rule live in `electron/setup-guards.ts`. While setup is incomplete, the workspace's New recording dialog shows that line and keeps **Start recording** disabled. The dialog also shows a refused start's error, and opening it clears an error left from an earlier action.
- **A replay and a recording never overlap.** A replay that passes its guard counts itself in `setupReopenings` until its save settles, and `onboardingComplete` changes only when that save lands. Meanwhile `startRecording` refuses with "Finish setup before starting a recording." and the companion tray refuses with "Finish setup to use the companion." even though `onboardingComplete` is still true. `startRecording` marks itself as changing state before its first await, so a replay handled while a recording is starting is refused with "Stop the recording before replaying setup." instead. Whichever call the main process handles first refuses the other.
- **The companion stays hidden while setup is open.** Its chat/record tray refuses to open until setup completes ("Finish setup to use the companion."). Screenshots and pointer overlays conceal the setup window like every other OpenMuse window: it is listed in `openMuseWindows()`, and `conceal()` (`electron/window-occlusion.ts`) fades it out for the capture and back in afterwards. Nothing is hidden or re-shown, so a replay during a capture leaves the companion hidden.
- **Preference saves resync windows only when the change includes `onboardingComplete`.** Picking a companion in Settings does not refocus or recreate an open setup window, or re-show a hidden companion. A save whose change includes `onboardingComplete` resyncs even if the value is unchanged. A plain companion change still re-renders through the existing broadcast.
- **Closing the window skips setup.** Closing marks setup complete without marking any permission granted; recording still requires Accessibility and says so. If the skip cannot be saved, the cause is logged to the console and a non-blocking dialog on the setup window says the settings could not be saved: check free disk space and folder permissions, then close the window again. The window stays open. Quitting is not a skip: while the app quits, the close handler returns before it blocks the close, so `onboardingComplete` stays false on disk and the next launch shows setup.
- **Quitting during a window load shows no dialog.** Quitting aborts a setup or chat window load that is still running, and neither window reports that as a load failure, because a dialog then would hold up the quit. Finishing or skipping setup can also destroy the setup window while it loads, which is not a failure either.
- **Every window gets the main process's own error text.** The preload strips Electron's "Error invoking remote method …" prefix from every call. The workspace, the companion and its chat show the message as the main process wrote it; the setup window shows its own fixed messages and logs the main process's message to the console (see Errors).
- **Permission status is never inferred.** On the Permissions screen, status is re-read every 2 seconds and when the window regains focus, with at most one check in flight. A failed check shows an inline error with **Try again** and keeps the last known status.
- **Restarts.** If macOS relaunches the app after a Screen Recording change, setup opens again from Welcome and each row reflects the real status.

## Preferences and IPC

- `Preferences` becomes `{ companion, onboardingComplete }`. At startup main.ts calls `startupPreferences(path, libraryPath)` before `Store.load()` creates the library. It sets `returningInstall` to whether the `library` folder exists and loads the file with `loadPreferences(path, returningInstall)`, whose missing-file default is `{ companion: "capybara", onboardingComplete: returningInstall }`. When no file existed and the install is new, it saves that default, so the file records that setup is unfinished. A returning install without a file writes nothing until a preference changes. `loadCompanion` and `saveCompanion` are gone.
- Loading drops any key it does not know (for example `activeThreadId`, written by the Rich Threads build that shares this same file) instead of failing startup. Known-field validation is unchanged: an invalid `companion`, a non-boolean `onboardingComplete`, or an invalid `placement` still fail. Stored files may still contain the legacy `placement` field (`"notch"` or `"floating"`); loading accepts it and drops it, and the next save writes the file without it. A file that cannot be checked or read, is not valid JSON or fails validation throws `Could not read <path>: <reason> Fix or delete this file, then reopen OpenMuse.` Saving stays strict: it rejects `placement`, any other unknown key such as `activeThreadId`, and a missing field, before writing anything.
- Saving writes a private temporary file beside the preferences file and renames it into place. If creating the folder, the write or the rename fails, `savePreferences` removes the temporary file and throws `Could not save <path>: <reason> Check free disk space and folder permissions, then try again.`, which names the preferences file, not the temporary one. The reason is "Permission denied.", "The disk is full." or "The disk is read-only." for those failures, and Node's own message otherwise. A `library` folder that cannot be checked fails startup with `Could not open <library>: <reason> Make sure this folder can be opened, then reopen OpenMuse.`, using the same reasons.
- New IPC `openPermissionSettings(kind)` accepts only `"accessibility"` or `"screenCapture"` and opens a fixed System Settings URL chosen in the main process. It goes through the existing trusted-sender check, which now covers the setup window instead of the notch window. Settings → macOS permissions offers the same button per row, through the same IPC, shown only while that permission is not granted and named per row (for example "Open System Settings for Accessibility").
- `completeOnboarding(options?: { openWorkspace?: boolean })` saves `onboardingComplete: true` first and opens the workspace only after that save resolves, so a failed save's error stays visible in the setup window rather than behind a workspace that opened anyway. It refuses unknown option keys. `replayOnboarding` (`replaySetup` in main.ts) throws before saving anything while a recording is active or still starting; once past that check, it counts itself in `setupReopenings` until its save settles.
- The preload sends every call through one `invoke` helper, which strips Electron's `Error invoking remote method '<channel>':` prefix and the error name after it from a rejection, so each window gets the main process's own message. App.tsx no longer has its own `ipcMessage` helper.

## Testing

- `tests/preferences.test.ts`: `startupPreferences` saves only a new install's defaults, shows setup again after a first launch that fails once the library exists, and fails with the library path when it cannot check the library. It also covers missing-file defaults, private atomic and strict saves, a failed save that names the file and leaves no temporary file behind, legacy `placement` and unknown keys dropped on load and by the next save, and invalid or unreadable files failing with the file path.
- `tests/setup-guards.test.ts`: replay is refused while a recording is active or changing state; recording is refused while setup is incomplete or reopening; both are allowed otherwise.
- `tests/notch-geometry.test.ts` is deleted with the notch. The other unit test files come from `main`, and this branch does not change them.
- `scripts/smoke.mjs`: launches the app with Playwright on four fresh data folders (a first launch, a relaunch mid-setup, a legacy preferences file and a returning install), fails on any renderer error or a quit that takes over 20 s, and prints one ledger line per check with the reason for each skip. `docs/verification.md` quotes the ledger from the 2026-09-25 run.
- `docs/verification.md` also records which checks passed and what was not run: the packaged smoke (`npm run smoke:packaged`), a signed build, and granting a permission in System Settings, which stays a user action.
